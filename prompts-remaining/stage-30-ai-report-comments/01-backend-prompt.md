Read `docs/14-module-academic-results.md` §10 and `docs/19-unique-differentiators.md` §4 before starting. The constraint that matters most in this whole stage: **the suggestion is a draft, never an auto-publish** — every line of the implementation should make that constraint mechanically true, not just true by convention.

## 1. `CommentSuggestionModule`
- `POST /results/:armId/:termId/students/:studentId/suggest-comment` — `@Roles('CLASS_TEACHER', 'ADMIN')` (the two roles who actually write the comment fields this assists — form-teacher comment and principal's comment respectively, per Stage 5's existing fields). Server-side, assemble the student's actual term data — score trend across the term's assessment components (reuse Stage 5's `Score`/`Result` data), attendance rate (Stage 4), conduct ratings (Stage 5's affective/psychomotor data) — and send it to Claude (use the Anthropic SDK, model `claude-sonnet-4-6` or later per this project's own convention of defaulting to current-generation models) with a prompt that asks for a short, specific, non-generic comment grounded in that actual data, not a template with the name swapped in.
- The response is **returned to the frontend, never written to the database**. There's no `POST .../comment` variant here that saves directly — the only way a comment reaches `Result.formTeacherComment`/`Result.principalComment` is through the **existing** Stage 5 comment-saving endpoint, which a human explicitly submits after reviewing (possibly editing) the suggestion. This stage adds a suggestion source, not a second save path.
- Rate-limit this endpoint (reuse `@nestjs/throttler` from Stage 11) — an LLM call per request has a real cost, and a Class Teacher batch-clicking through 40 students' worth of suggestions is the expected normal usage pattern, not abuse, but it should still have a sane per-minute ceiling to avoid runaway cost from a bug or a moment of the UI making rapid duplicate calls.
- Log the suggestion (prompt input summary + output) to `AuditLog` for traceability, **but explicitly don't log full student PII into a third-party API call beyond what's pedagogically necessary** — first name and the term's data points are enough; don't send the student's full bio-data, guardian contact info, or anything outside what shapes a fair, specific comment.

**Done when**: requesting a suggestion for a real seeded student returns a comment that's actually specific to that student's score trend and attendance (not generic boilerplate — spot-check by comparing two students with very different terms and confirming the suggestions differ meaningfully), the suggestion never lands in the database until a teacher explicitly saves it through the existing comment-save endpoint, and a deliberately rapid burst of suggestion requests is correctly rate-limited rather than running up an unbounded API bill.
